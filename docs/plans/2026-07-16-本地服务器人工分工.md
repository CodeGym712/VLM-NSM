# VLM-NSM 本地—服务器—人工分工与交接规范（2026-07-16）

> **本规范优先于临时任务描述。**
>
> 核心原则：**本地拥有系统语义、主线代码、修复与最终验收权；服务器提供显存和算力，用于执行已冻结的计算任务；人工只提供独立盲审标注。** 服务器结果未经本地审计，不进入系统结论。

## 1. 一句话分工

| 端 | 唯一职责 | 不能替代的职责 |
| --- | --- | --- |
| 本地 | 复杂系统主线开发、逻辑修复、数据/语义契约、审计和发布 | 决定“系统应该是什么”和“结果是否成立” |
| 服务器 | GPU/显存密集训练、真实环境大规模回放、批量数据生成 | 在冻结规范下决定“能否跑完”和“得到哪些原始结果” |
| 人工 | P3-E 等独立盲审与不确定项标注 | 提供不依赖系统预测的外部证据 |

## 2. 本地端：主线开发与验收所有者

本地端负责一切需要理解全局语义、改动系统行为或判断结论是否成立的工作：

1. **主线设计与修复**：operator/domain 语义、predicate/role binding、planner、witness、resolver、训练数据契约及其 bug 修复；
2. **R2/R3/R4 逻辑工作**：event-effect binding、applicability、反事实 witness、最小子句修订、特异性对照、组合泛化的指标定义；
3. **工程质量**：单元测试、回归测试、schema、JSONL 字段、输入/输出 hash、manifest、审计脚本和可复现实验命令；
4. **服务器回传验收**：独立复算统计、核验 SHA-256/环境版本/输入 hash、检查逐条记录及结论边界；
5. **知识与版本管理**：更新 Obsidian、维护任务单、整理 Git 分支、提交和推送经过验收的最小变更集；
6. **最终裁决**：决定结果是 PASS、需修复，还是只能作为 smoke/辅助证据。

本地端不把等待服务器作为逻辑开发的前置条件。能以合成状态、小样本或纯 Python 验证的部分，应先在本地形成可测试的契约和审计器。

## 3. 服务器端：显存与真实环境执行者

服务器只执行已由本地冻结的、资源密集型任务：

1. GPU/显存密集训练：diffusion、BC、DAgger、视觉策略、共享策略及超参扫描；
2. LIBERO BDDL + MuJoCo 的全量或大样本 replay、真实 predicate 重算和环境交互；
3. 大规模 demo/video/rollout 收集、严格训练/测试切分评估，以及本地显存不足的批量任务；
4. 按指定命令在固定版本上运行，并返回原始结果包。

服务器**不得**自行修改主线代码、operator 语义、字段契约、阈值、候选定义或结论措辞；不得以手工汇总替代逐条 JSONL；不得把 smoke、手写编辑或单环境回放表述为 learned revision 或 OOD 结论。发现定义、环境或数据问题时，应停止扩展结论并回报本地，而不是自行“修正”任务。

## 4. 固定交接协议

### 本地 → 服务器：任务包

每个服务器任务必须给出：

- 任务 ID、目的、允许的结论范围和明确的 PASS/FAIL 条件；
- 对应 Git commit SHA（或冻结补丁）与精确执行命令；
- 输入文件清单及 SHA-256、样本范围、随机种子和数据切分；
- 输出 schema：逐条 JSONL、汇总 JSON、报告、`environment_versions.json`、`command_log.txt`、`manifest.sha256`；
- 必须保留的失败/阻塞分类，不允许只返回成功摘要。

### 服务器 → 本地：证据包

服务器返回可在本地读取的完整目录；通过用户指定的传递方式进入本地目录，不使用 `scp`。证据包至少包含：

- 原始逐条结果和输入副本/输入 hash；
- 汇总报告及可由逐条记录复算的统计；
- 运行命令、环境版本、依赖/模型版本、随机种子；
- 覆盖所有交付文件的 SHA-256 manifest；
- 明确的失败、跳过和阻塞原因。

### 本地验收闸门

1. 先验 manifest 与输入 hash；
2. 从 JSONL 重算报告统计并核对逐条状态；
3. 核验任务是否满足冻结的语义与反事实条件；
4. 只有本地审计标记为 **PASS**，该包才可推动下一阶段或进入论文/汇报结论；否则回到“修复任务包”，不以摘要替代修复。

## 5. GitHub 同步规则

Git 的唯一写入/发布端为本地：本地创建分支、审查差异、提交、推送；服务器只消费固定 commit 并返回结果包。这样能防止环境端的临时改动覆盖系统语义。

一次同步只包含一个已验收的最小主题，不混入目录重组、演示产物、模型权重、临时缓存或其他未审查修改。推荐顺序：

1. 本地核验 R2/R3 结果和相关测试；
2. 仅暂存本主题的代码、测试、审计脚本、精简报告/manifest 与本规范；
3. 在 `codex/` 前缀分支形成清晰 commit；
4. 推送后，以该 commit SHA 作为下一次服务器任务的唯一代码基线。

## 6. 当前阶段的执行落点

- R2 v3 和 R3 witness acceptance：服务器提供证据包，本地负责完整性和语义审计；通过后才可作为正式交接证据。
- R3 specificity：本地先维护无混杂的状态/逻辑回归；服务器只在需要真实 LIBERO/MuJoCo 大规模复现时执行冻结任务包。
- 后续训练、全量回放、视频/策略评估：服务器执行；训练目标、指标、失败分类和结论解释始终由本地定义与验收。

## 7. 每轮结束的固定输出

每次检查或完成一个任务后，本地必须写明：

1. 已核验的证据与结论边界；
2. 下一阶段的本地任务；
3. 如需服务器，给出服务器任务包所需输入、输出和验收条件；
4. 如需同步，列出可安全进入本次 Git commit 的精确文件范围。
